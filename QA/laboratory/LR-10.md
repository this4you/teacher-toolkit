# Лабораторна робота: Mocking, інтеграційні тести та CI/CD (GitHub Actions)

## Мета
1. Закріпити **mocking** у unit-тестах (ізольоване тестування логіки).
2. Навчитися писати **інтеграційні тести** (реальні залежності, наприклад Postgres у контейнері).
3. Налаштувати **CI/CD у GitHub Actions**, щоб PR не проходив перевірку, якщо тести/coverage не відповідають вимогам.

---

## Що ви отримуєте
Вам надається репозиторій з базовим кодом `OrderService` та **стартовими тестами**, які навмисно покривають приблизно **~30%** логіки.

Ваше завдання — **дописати тести** (і невеликі налаштування за потреби), щоб виконати вимоги лабораторної.

---

## Вимоги до оточення
- **Node.js**: 18+ (рекомендовано LTS)
- **npm**: 9+ (йде разом з Node)
- **Git**: встановлений
- ОС: Windows / macOS / Linux

> Порада: якщо у вас декілька версій Node, використовуйте `nvm` (опційно).

## 1) Як клонувати репозиторій
1. Скопіюйте URL репозиторію (викладач надасть).
2. Виконайте в терміналі:

```bash
git clone <REPO_URL>
```

## 2) Встановлення залежностей
У корені репозиторію виконайте:

```bash
npm install
```

---

## 3) Запуск тестів локально
### Запуск усіх тестів
```bash
npm test
```

### Запуск тестів з coverage
```bash
npm run test:coverage
```

Після запуску coverage у консолі ви побачите відсотки покриття. Також з’явиться папка `coverage/` (локально).

---

## 4) Опис задачі лабораторної
В репозиторії є сервіс `OrderService`, який:
- валідовує інпут,
- рахує subtotal/discount/shipping/tax,
- застосовує risk-rules,
- викликає `paymentClient.charge(...)`,
- при успіху надсилає email через `emailClient.send(...)`,
- при відмові платежу кидає помилку і **не** надсилає email.

Стартові тести покривають лише:
- happy-path (approved),
- validation: empty items.

---

## 5) Що потрібно зробити (вимоги)
### A. Unit-тести з mocking (обов’язково)
Напишіть unit-тести для `OrderService`, використовуючи **моки** для:
- `PaymentClient`
- `EmailClient`

У тестах перевіряйте не тільки результат, а й **виклики моків**: кількість викликів, параметри, що email не викликається у негативних сценаріях.

### B. Інтеграційні тести (по бажанню)
Додайте **інтеграційні тести** з реальною БД:
- підняти **PostgreSQL у Docker** (через GitHub Actions services — у CI, і через docker compose або командою локально),
- реалізувати простий `OrderRepository` (або модуль з записом/читанням замовлень),
- інтеграційно перевірити, що дані реально записуються/читаються.

> Дозволено використати будь-яку технологію доступу до БД: `pg`, `knex`, `typeorm`, `prisma` — на ваш вибір (краще `pg` або `knex` для простоти).

### C. GitHub Actions (обов’язково)
Налаштуйте workflow, який запускається на:
- `pull_request`
- `push` у `main`

Workflow має:
1. встановлювати залежності (`npm ci`);
2. запускати unit + integration тести;
3. перевіряти coverage і валити pipeline, якщо він нижчий за поріг.

---

## 6) Мінімальні критерії здачі
✅ Репозиторій містить:
- нові/оновлені unit-тести з mocking;
- `.github/workflows/ci.yml` (або аналог) з GitHub Actions;
- README або цей документ з короткими командами запуску.

✅ У GitHub Actions на PR:
- pipeline проходить,
- видно тестовий прогін,
- coverage відповідає вимогам.

---

## 7) Coverage-вимоги
- **Statements / Branches / Functions / Lines**: **80%+** (мінімум)
- Важливо: покриття має бути не “накручене”, а змістовне: тести на ключові гілки логіки.

---

## 8) Список того, що потрібно покрити тестами (checklist)
Нижче — список **обов’язкових** сценаріїв (мінімум). Ви можете додати більше.

### 8.1 Validation
- [ ] invalid email (без `@`) → `VALIDATION: invalid email`
- [ ] empty items → `VALIDATION: empty items` (вже є)
- [ ] invalid sku (порожній) → `VALIDATION: invalid sku`
- [ ] invalid qty (0 / від’ємний / не integer) → `VALIDATION: invalid qty`
- [ ] invalid price (<= 0 або NaN/Infinity) → `VALIDATION: invalid price`

### 8.2 Coupons / Discount
- [ ] `SAVE10` → знижка 10%
- [ ] `SAVE20` → знижка 20%
- [ ] `WELCOME...` → 5% але максимум $15 (1500 cents)
- [ ] unknown coupon → `VALIDATION: unknown coupon`
- [ ] coupon trimming/case-insensitive (наприклад `" save10 "`)

### 8.3 Shipping
- [ ] shipping безкоштовний при subtotal >= 5000 cents
- [ ] shipping платний при subtotal < 5000 cents
- [ ] USD vs EUR базова доставка (перевірити різницю)

### 8.4 Tax
- [ ] EUR VAT 20%
- [ ] USD tax 8.25%
- [ ] taxable <= 0 → tax 0

### 8.5 Risk rules
- [ ] email `@tempmail.com` → `RISK: tempmail is not allowed`
- [ ] total > 200000 cents → `RISK: amount too high`
- [ ] email містить `+` і total > 50000 → `RISK: plus-alias high amount`

### 8.6 Payment + Email behavior
- [ ] payment declined → error `PAYMENT_DECLINED: ...` і **email НЕ надсилається**
- [ ] approved → email надсилається 1 раз, з очікуваними параметрами
- [ ] перевірити, що `paymentClient.charge` викликається з коректною сумою/валютою

### 8.7 Edge cases (мінімум 1-2)
- [ ] округлення cents для price з дробами (наприклад 10.005)
- [ ] декілька items → коректний subtotal
- [ ] discount не робить total від’ємним (Math.max(0, ...))

---

## 9) Як здавати
1. Зробіть **fork** репозиторію у свій GitHub.
2. Реалізуйте зміни в окремій гілці.
3. Відкрийте Pull Request у вашому репозиторії (або в fork → main).
4. Переконайтесь, що GitHub Actions **зелений** ✅
5. Надішліть:
    - посилання на ваш репозиторій,
    - посилання/скрін проходження GitHub Actions (workflow run).

---

## 10) Поради
- Пишіть тести “Given / When / Then” (коментарями або структурою).
- Не використовуйте `setTimeout` без потреби — краще мокати час/рандом при необхідності.
- Для інтеграційних тестів — робіть **ізольовані** дані (clean-up після тестів).
- Тримайте тести швидкими: unit — мілісекунди, integration — секундні.
